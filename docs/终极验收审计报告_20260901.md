### 5.2 【代码隐患·未实测】费用化共用支出分摊到"已形成"资本化项目时,限额基数可能重复计算

`src/summary.js:92–100` 的 `capIn` 池循环,判定条件为:

```js
if (!projMap[a.projectId] || projMap[a.projectId].capitalization !== 'capitalize') return;
if (!formed.has(a.projectId)) return;
capIn.capitalize[exp.category] = round2(capIn.capitalize[exp.category] + a.amount);
```

**只按目标项目(a.projectId)的 `capitalization` 判定,未检查源费用 `exp.capitalization`。**

- 主池 `pool` 按**源费用**属性归入 expense/capitalize
- `capIn` 按**目标项目**属性归入 capitalize

若一笔**费用化**共用支出(如共用折旧)分摊到**已形成无形资产**的资本化项目,同一笔钱会同时进入 `pool.expense`(计入 base5)与 `capIn.capitalize`(计入 base5CapF)→ `otherLimit = (base5 + base5CapF) ÷ 9` 中该份额被**重复计算**,导致其他费用限额、境外 2/3 限额虚增。

**触发条件**(需同时满足):① 共用费用(ratioHours/ratioCustom)② 源费用为费用化 ③ 分摊到资本化项目 ④ 该资本化项目已有摊销记录。

**本例不触发**(唯一共用折旧全额归费用化项目 RD-01,且 RD-02 无摊销记录)。

> MANUAL_REVIEW:属代码级推理,本轮按"不编码"要求未构造场景实测。建议补一行源属性过滤:
> `if (expenseTypeOf(exp, projMap[exp.projectId]) !== 'capitalize') return;`

### 5.3 【业务漏洞·结构未变】P0-2 的漏加计风险可能仍在

新代码解决了**口径**问题(未形成项目的资本化支出不进限额基数),但**归属**问题未解决:

- 资本化源费用按工时分摊到**费用化**项目时,该份额仍按源属性进入 `pool.capitalize` → 计入 `capitalFormed`
- 但 `capIn` 不收(目标项目非资本化)→ 不进限额基数
- 摊销计划接口仍要求 `project.capitalization === 'capitalize'` → **费用化项目无法生成摊销**

→ 该份额既不在费用化加计基数,也无法摊销加计,**仍可能永久漏计**。

**本例不触发**(无资本化源共用支出)。

> MANUAL_REVIEW:需构造场景实测确认。

### 5.4 【数据缺失】节税测算无意义

`companies.json` 仅有 `name / industry / taxNo / creditCode`,**无 `revenue` / `taxableIncome`** → 应纳税所得额取 0 → 节税额 = 0。首页"预计节税"卡片显示 0,无法反映真实节税效果。建议在"企业设置"补录 2026 年营业收入与应纳税所得额。
